## Context

Мотивация — в `proposal.md` («Why»), требования — в
`specs/deployment/staging/spec.md`.

Что есть сейчас:

- `docker-compose.yml` в корне — исключительно dev-профиль: bind-mount кода
  внутрь контейнеров, vite dev-сервер на 5173 за проксёй nginx, MySQL наружу на
  `3306`, nginx проекта на `80:80`, данные MySQL — bind-mount в
  `docker/mysql/var/mysql` (каталог в `.gitignore`).
- `docker/nginx/default.conf` разводит два виртуальных хоста по `server_name`:
  `api.localhost` -> php-fpm и `localhost` -> `frontend:5173`.
- Бэкенд: Symfony 6.4 / PHP 8.4, JWT (Lexik), ключи в `backend/config/jwt/*.pem`
  (в `.gitignore`), загруженные шаблоны — в `backend/var/document-templates`
  (`/var/` целиком в `.gitignore`), health-эндпоинт `/api/v1/health` уже открыт
  (`PUBLIC_ACCESS` в `security.yaml`).
- Фронтенд: Vite 5, `src/config/api.js` склеивает `VITE_API_URL` с суффиксом
  `/api/v1`; в `frontend/.env.production` сейчас `VITE_API_URL=https://api.appbankrot.ru`.
- `.env.stage` и `.env.prod` бэкенда лежат в git с реальными `APP_SECRET` и
  `JWT_PASSPHRASE`; в `.env.stage` вдобавок `APP_ENV=dev`.

Ограничения целевого сервера (`8433335-vb908828`):

- Host-nginx терминирует TLS и проксирует на loopback-порты контейнеров.
  Заняты `127.0.0.1:8091` (promo-nginx), `8092` (raschetnik-varnish),
  `8093` (alimenty-varnish). Свободен `8094`.
- Соседние проекты не публикуют порты БД и держат php-fpm на внутреннем `9000`.
- Каталоги проектов — `/srv/sites/<домен>`; конфиги host-nginx —
  `/etc/nginx/sites-available/<домен>.conf`.
- Соседи используют PostgreSQL 16; мы остаёмся на MySQL 8 — это осознанное
  отличие, порт `3306` внутри своей сети ни с кем не конфликтует.

## Goals / Non-Goals

**Goals:**

- Один compose-файл для сервера, не ломающий `make up` для локальной разработки.
- Образы самодостаточны: код, `vendor/` и собранная статика внутри, никаких
  bind-mount исходников в проде.
- Состояние (база, `var/document-templates`, `config/jwt`) — только в именованных
  томах.
- Деплой — идемпотентный SSH-скрипт, повторный запуск на том же коммите
  безопасен.

**Non-Goals (в дополнение к разделу «Вне рамок» проповала):**

- Оптимизация размера образов и времени сборки.
- Общий базовый образ для dev и prod: dev остаётся на текущих Dockerfile.
- Автоматизация настройки host-nginx и выпуска сертификата — делается руками
  один раз.

## Decisions

### Решение 1. Отдельный `compose.prod.yml` вместо override-файла

Берём самостоятельный `compose.prod.yml` с собственными именами сервисов,
контейнеров (`bankrot-nginx`, `bankrot-php`, `bankrot-mysql`), сети и томов.

Почему не `docker-compose.override.yml` / `-f docker-compose.yml -f prod.yml`:
prod отличается от dev не настройками, а устройством — вместо bind-mount кода
сборка образа, вместо vite dev-сервера статика, другой набор томов, другой
nginx-конфиг. Наложение потребовало бы «отменять» почти каждый ключ базового
файла (в частности, bind-mount `./backend:/var/www/html` перекрыл бы код,
вкомпилированный в образ), что читается хуже, чем два независимых файла.

Побочный плюс: имена контейнеров `bankrot-*` не конфликтуют с локальными
`bankruptcy-*`, если кто-то поднимет проект на той же машине.

### Решение 2. Раздача SPA и API одним nginx проекта

Внутри проекта один контейнер nginx с единственным `server`-блоком на `:80`:

- `location /api` -> `fastcgi_pass php:9000` (включая `/api/doc`);
- `location /` -> `try_files $uri /index.html` по собранной статике фронтенда.

Порядок важен: `location /api` должен выигрывать у корневого, иначе SPA начнёт
перехватывать запросы API. Статика попадает в образ nginx на этапе сборки
(multi-stage: `node:20-alpine` собирает `dist`, результат копируется в
`nginx:stable-alpine`), а не монтируется томом — так выкладка атомарна на
уровне образа.

Почему не вариант «SPA отдаёт php-контейнер из `backend/public`»: пришлось бы
класть сборку фронтенда внутрь бэкенда и разруливать конфликт `try_files` с
`index.php`. Почему не отдельный поддомен `api.*` — выбор пользователя, см.
`proposal.md`; попутно исчезает CORS-preflight на каждом запросе.

Требование спецификации о редиректе `http -> https` реализуется на host-nginx,
а не внутри контейнера: TLS терминируется снаружи. Контейнер должен доверять
`X-Forwarded-Proto` (`fastcgi_param HTTPS`, `trusted_proxies` в Symfony), иначе
Symfony будет генерировать абсолютные ссылки по `http`.

### Решение 3. `VITE_API_URL` пустой, пути относительные

`src/config/api.js` уже приводит базу к виду `<base>/api/v1`, а при пустой базе
даёт относительный `/api/v1`. Поэтому в `frontend/.env.production` ставим
`VITE_API_URL=` и ничего в коде не меняем. Это же снимает необходимость
пересобирать фронтенд при смене домена.

Альтернатива — прописать абсолютный `https://bankrot.shefcode.tech` — работает,
но зашивает домен в бандл и возвращает CORS.

### Решение 4. Секреты — переменные окружения в `compose.prod.yml`

Все значения задаются через `environment:` сервисов и подставляются из файла
`.env` рядом с `compose.prod.yml` (не в git, создаётся из отслеживаемого
`compose.prod.env.example`): `APP_SECRET`, `JWT_PASSPHRASE`,
`MYSQL_ROOT_PASSWORD`, `MYSQL_PASSWORD`, `HTTP_PORT`, `CORS_ALLOW_ORIGIN`,
`TRUSTED_PROXIES`. `DATABASE_URL` собирается в compose из реквизитов MySQL,
поэтому пароль базы задан ровно в одном месте. Отсутствие обязательного
секрета валит `docker compose config` (синтаксис `${VAR:?сообщение}`), а не
всплывает уже в рантайме.

Первоначально планировался `backend/.env.local` на сервере, но этот вариант
не работает: Symfony Dotenv грузит файлы в порядке `.env` -> `.env.local` ->
`.env.$APP_ENV` -> `.env.$APP_ENV.local`, то есть `backend/.env.prod` из образа
перекрыл бы `.env.local`. Реальные переменные окружения, наоборот, имеют
приоритет над всеми dotenv-файлами — Dotenv не перезаписывает уже заданные
значения. Поэтому конфигурация идёт через окружение контейнера.

Отслеживаемые файлы чистим: `backend/.env.stage` удаляем (он существовал
только ради старого шага `cp .env.stage .env`), в `backend/.env.prod`
оставляем структуру с пустыми значениями.

Значения `APP_SECRET` и `JWT_PASSPHRASE`, лежащие в git (`backend/.env`,
`backend/.env.dev`, `backend/.env.test`), остаются как локальные dev-умолчания,
но для развёрнутой системы считаются скомпрометированными: на сервере задаются
новые.

Альтернатива — GitHub Secrets + генерация файла окружения на каждом деплое:
даёт единый источник, но добавляет риск затереть рабочую конфигурацию сервера
пустым секретом и требует хранить `DATABASE_URL` в CI. Для одного контура
избыточно.

### Решение 5. Состояние — именованные тома

Три тома в `compose.prod.yml`:

| Том | Куда монтируется | Что хранит |
|---|---|---|
| `bankrot-db` | `/var/lib/mysql` контейнера MySQL | база |
| `bankrot-var` | `/var/www/html/var` контейнера php | `document-templates`, кэш, логи |
| `bankrot-jwt` | `/var/www/html/config/jwt` контейнера php | пара `*.pem` |

`bankrot-var` монтируется поверх `var/` из образа — Symfony создаст `cache` и
`log` сам при прогреве. Ключи JWT генерируются один раз при первой установке
(`make jwt-gen` внутри контейнера) и дальше живут в томе, поэтому исчезает
вся логика бэкапа `config/jwt` в `/tmp` из старого workflow.

Не используем bind-mount в `/srv/sites/...`, как `docker/mysql/var/mysql`
локально: именованный том не зависит от прав пользователя на хосте и не
попадает под `git clean`.

### Решение 6. Деплой — `git pull` + пересборка на сервере

Шаг деплоя в workflow — один `appleboy/ssh-action` со скриптом:

1. `cd /srv/sites/bankrot.shefcode.tech && git fetch --prune && git reset --hard origin/staging`
   (`reset --hard`, а не `pull`: каталог сервера — реплика ветки, локальных
   правок там быть не должно, а `pull` вставал бы на конфликтах);
2. `docker compose -f compose.prod.yml build`;
3. `docker compose -f compose.prod.yml up -d`;
4. ожидание готовности MySQL, затем `docker compose exec -T php make db-migrate`
   и `make cc`;
5. проверка `curl -fsS http://127.0.0.1:8094/api/v1/health`.

Composer-зависимости ставятся на этапе сборки образа
(`composer install --no-dev --optimize-autoloader`), а не на живом сервере —
падение сети во время `composer install` больше не оставляет систему с
полусобранным `vendor/`.

Порядок «сначала контейнеры, потом миграции» означает, что между стартом нового
кода и применением миграции есть окно в несколько секунд. Для одного staging-
контура это принято; zero-downtime — вне рамок.

Аутентификация SSH — по ключу (`key: ${{ secrets.STG_SSH_KEY }}`), а не по
паролю, как сейчас. Новые секреты: `STG_SSH_HOST`, `STG_SSH_USER`,
`STG_SSH_KEY`, `STG_PROJECT_DIR`.

### Решение 7. Пути в джобах качества

Джобы PHPStan / CS Fixer / PHPUnit / `tsc` сохраняются, но
`working-directory: ${{ secrets.LOCAL_BACKEND_DIR }}` заменяется на явные
`backend` и `frontend`. Путь внутри репозитория — не секрет; сейчас из-за этого
workflow нечитаем и ломается у любого, у кого секрет не задан.

Тесты продолжают гоняться на SQLite (`make test` -> `test-prepare`), сервис
MySQL в CI не поднимаем.

### Решение 8. Health-check MySQL и порядок запуска

`depends_on` с `condition: service_healthy` для MySQL (healthcheck через
`mysqladmin ping`), иначе php стартует раньше базы и первый же `db-migrate`
падает. У nginx — `depends_on: php`.

### Решение 9. Отдельное имя проекта compose

`compose.prod.yml` объявляет `name: bankrot-prod`. Без этого compose берёт имя
проекта из каталога — `bankrot`, то есть ровно то же, что у dev-профиля, и
`docker compose -f compose.prod.yml up` пересоздаёт dev-контейнеры вместо
запуска отдельного стека (проверено: `bankruptcy-php`, `bankruptcy-mysql` и
`bankruptcy-nginx` были пересозданы). На сервере конфликт бы не проявился, зато
локальная проверка prod-профиля ломала бы разработку.

### Решение 10. Цепочка миграций чинится, а не обходится

`make db-migrate` на пустой базе падал: `Version20250124000000` (24.01.2025)
правит таблицу `contracts`, которую создаёт `Version20251107134535`
(07.11.2025) — на две позиции позже. Схема первоначально создавалась не
миграциями, поэтому расхождение не всплывало.

Чиним двумя правками:

1. В `Version20250124000000` добавлен `skipIf` по наличию таблицы `contracts` —
   на пустой базе миграция пропускается, на существующей работает как раньше.
2. Новая `Version20260905090000` приводит `contracts` к сущностям: заменяет
   уникальный индекс по `court_id` обычным (иначе на чистой базе нельзя завести
   два дела в одном суде), удаляет осиротевшие `manager_id`, `sex`,
   `judicial_realization_decision_date`, `judicial_realization_resolution_date`
   и внешний ключ `FK_950A973783E3463`. Все операции защищены проверками
   существования, поэтому миграция безопасна и на пустой, и на существующей
   базе. `down()` объявлена необратимой.

Альтернативы: `doctrine:schema:create` + `migrations:version --add --all` при
установке (репозиторий не трогается, но проблема возвращается при следующей
установке с нуля) и схлопывание 56 миграций в одну baseline (переписывает
историю и требует ручной отметки на старом сервере).

## Risks / Trade-offs

- **Порт 8094 может оказаться занят к моменту установки** → перед первой
  выкладкой проверить `ss -ltnp | grep 8094`; порт вынесен в переменную
  окружения compose (`HTTP_PORT`), смена не требует правки кода.
- **Сборка на сервере грузит общий CPU и может задеть соседей** → сборка
  запускается только на push в `staging`; при частых деплоях перейти на
  Решение «образы в GHCR» (сейчас вне рамок).
- **`git reset --hard` затрёт ручные правки на сервере** → все изменяемые
  файлы (`backend/.env.local`, `.env` рядом с compose) добавлены в
  `.gitignore` и не отслеживаются; правило «на сервере руками код не правим»
  фиксируется в README.
- **Первая выкладка на пустой базе оставит систему без пользователей** →
  задача установки включает ручное заведение администратора; без него в
  систему не войти.
- **Потеря тома `bankrot-var` = потеря всех загруженных шаблонов документов**
  → резервное копирование вне рамок, но факт зафиксирован в README, чтобы это
  не стало сюрпризом.
- **Symfony в `prod` кэширует конфигурацию** → `make cc` обязателен в скрипте
  деплоя; без него правки конфигов не подхватятся.
- **Смена `APP_ENV` с `dev` на `prod`** может вскрыть ошибки, замаскированные
  dev-режимом (отсутствующие переменные окружения, строгий контейнер) → первая
  выкладка проверяется вручную по чек-листу задач, а не только по health.
- **MySQL 8 против PostgreSQL 16 у соседей** → администратору сервера
  придётся обслуживать два движка; принято ради нулевого риска по миграциям
  Doctrine.

## Migration Plan

Разовая установка (руками, до первой автоматической выкладки):

1. DNS `bankrot.shefcode.tech` -> IP сервера.
2. `git clone` ветки `staging` в `/srv/sites/bankrot.shefcode.tech`.
3. Создать `backend/.env.local` и `.env` для compose с новыми секретами.
4. `docker compose -f compose.prod.yml build && up -d`, дождаться healthy MySQL.
5. `make db-migrate`, `make jwt-gen`, завести администратора.
6. Конфиг host-nginx `bankrot.shefcode.tech.conf` -> `proxy_pass
   http://127.0.0.1:8094`, `client_max_body_size 100M` (как в контейнерном
   конфиге сейчас), сертификат, `nginx -t && systemctl reload nginx`.
7. Проверить чек-лист сценариев из спецификации.
8. Прописать секреты GitHub, снести неиспользуемые `STG_FTP_*`.

Откат: `git reset --hard <предыдущий коммит>` в каталоге проекта и повторная
сборка. Данные при откате не трогаются; обратной миграции Doctrine скрипт не
выполняет — если откатываемая версия содержала миграцию, её нужно откатить
вручную (`doctrine:migrations:migrate prev`).

Старый контур `appbankrot.ru` остаётся работать до подтверждения нового; его
отключение — отдельная задача вне этого изменения.
