## Purpose

Описывает, как развёрнутая система доступна юристам на общем сервере: по какому
адресу открывается интерфейс и API, что должно пережить выкладку новой версии и
при каких условиях выкладка не выполняется.

## ADDED Requirements

### Requirement: Единый адрес системы

Система SHALL быть доступна юристам по адресу `https://bankrot.shefcode.tech`.
Интерфейс (SPA) и API MUST отдаваться с одного origin: SPA — по корню, API — по
префиксу `/api`. Обращение по `http://` MUST перенаправляться на `https://`
кодом 301.

#### Scenario: Открытие списка дел

- **WHEN** юрист открывает `https://bankrot.shefcode.tech/contracts`
- **THEN** отдаётся SPA (`index.html`), маршрут разбирает клиентский роутер, и
  экран списка дел отображается без ошибки 404 от сервера

#### Scenario: Прямой заход на маршрут карточки дела

- **WHEN** юрист открывает `https://bankrot.shefcode.tech/contract/17` по
  прямой ссылке или обновляет страницу на этом маршруте
- **THEN** сервер отдаёт `index.html` с кодом 200, а не 404

#### Scenario: Запрос к API с того же домена

- **WHEN** SPA выполняет запрос `POST https://bankrot.shefcode.tech/api/v1/login`
- **THEN** запрос обрабатывается бэкендом и браузер не выполняет CORS-preflight,
  поскольку origin запроса и origin страницы совпадают

#### Scenario: Обращение по незащищённому протоколу

- **WHEN** выполняется запрос `http://bankrot.shefcode.tech/contracts`
- **THEN** возвращается редирект 301 на `https://bankrot.shefcode.tech/contracts`

### Requirement: Изоляция от соседних проектов на сервере

Развёртывание SHALL не занимать порты, используемые другими проектами сервера.
Контейнеры проекта MUST публиковать наружу единственный порт — HTTP-вход
проекта — и только на loopback-интерфейсе `127.0.0.1`. Порт базы данных MUST NOT
публиковаться на хост. Имена контейнеров и docker-сеть MUST быть уникальны для
проекта.

#### Scenario: Выкладка при работающих соседях

- **WHEN** контейнеры проекта поднимаются на сервере, где уже работают
  `alimenty`, `raschetnik` и `promoscout` (заняты `127.0.0.1:8091`,
  `127.0.0.1:8092`, `127.0.0.1:8093`)
- **THEN** контейнеры стартуют успешно, ни один из соседних проектов не
  перезапускается и остаётся доступным по своему домену

#### Scenario: Попытка подключения к базе снаружи

- **WHEN** выполняется попытка подключиться к MySQL проекта с внешнего адреса
  сервера
- **THEN** соединение не устанавливается: порт не опубликован, база доступна
  только контейнерам внутри сети проекта

### Requirement: Сохранность данных между выкладками

Выкладка новой версии SHALL сохранять данные, накопленные в работе с делами.
Между выкладками MUST переживать пересборку: содержимое базы данных, загруженные
шаблоны документов всех категорий `BankruptcyStage` и пара JWT-ключей.

#### Scenario: Шаблоны документов после выкладки

- **WHEN** администратор загрузил шаблон категории `pre_court`, после чего
  выполнена выкладка новой версии
- **THEN** шаблон остаётся в списке шаблонов и по нему по-прежнему формируется
  документ

#### Scenario: Действующая сессия после выкладки

- **WHEN** юрист авторизован и получил JWT, после чего выполнена выкладка новой
  версии
- **THEN** ранее выданный токен продолжает приниматься до истечения своего срока:
  ключи подписи не перегенерируются

#### Scenario: Данные дел после выкладки

- **WHEN** выполнена выкладка новой версии
- **THEN** ранее заведённые дела, справочники и пользователи остаются в базе

### Requirement: Автоматическая выкладка по ветке staging

Push в ветку `staging` SHALL запускать выкладку. Выкладка MUST выполняться
только после успешного прохождения проверок качества бэкенда (PHPStan,
PHP CS Fixer, PHPUnit) и проверки типов фронтенда. При падении любой проверки
выкладка MUST NOT выполняться, а запущенная на сервере версия MUST остаться
прежней.

#### Scenario: Успешный push

- **WHEN** в ветку `staging` попадает коммит, проходящий все проверки
- **THEN** на сервере разворачивается код этого коммита, применяются миграции
  Doctrine, и система отвечает по адресу `https://bankrot.shefcode.tech`

#### Scenario: Push с ошибкой статического анализа

- **WHEN** в ветку `staging` попадает коммит, на котором падает PHPStan,
  PHP CS Fixer, PHPUnit или проверка типов TypeScript
- **THEN** шаг выкладки не выполняется и на сервере продолжает работать
  предыдущая версия

#### Scenario: Ручной запуск выкладки

- **WHEN** выкладка запускается вручную (`workflow_dispatch`) без изменений в
  коде
- **THEN** выполняются все проверки и выкладка текущего состояния ветки
  `staging`

### Requirement: Проверка работоспособности после выкладки

Развёрнутая система SHALL предоставлять публичную проверку работоспособности по
`GET /api/v1/health`, отвечающую кодом 200 без авторизации. Выкладка MUST
считаться успешной только после получения такого ответа; иначе выкладка MUST
завершиться ошибкой с записью в лог.

#### Scenario: Система поднялась

- **WHEN** после выкладки выполняется `GET https://bankrot.shefcode.tech/api/v1/health`
- **THEN** возвращается код 200 без заголовка `Authorization`, и выкладка
  помечается успешной

#### Scenario: Система не поднялась

- **WHEN** после выкладки `GET /api/v1/health` не отвечает кодом 200 в отведённое
  время
- **THEN** задание выкладки завершается с ошибкой, а в логе видны причины
  (вывод запуска контейнеров и миграций)

### Requirement: Секреты не хранятся в репозитории

Учётные данные развёрнутой системы SHALL задаваться на сервере и MUST NOT
находиться в git. Это касается `APP_SECRET`, пароля к базе данных, `JWT_PASSPHRASE`
и доступа к серверу. Развёрнутый бэкенд MUST работать в окружении `prod`:
профилировщик и отладочные страницы Symfony MUST быть недоступны.

#### Scenario: Ошибка приложения на развёрнутой системе

- **WHEN** запрос к API приводит к необработанному исключению
- **THEN** клиенту возвращается ответ об ошибке без трассировки стека, кода и
  значений переменных окружения

#### Scenario: Секреты в репозитории

- **WHEN** проверяется содержимое отслеживаемых git файлов окружения бэкенда
- **THEN** в них нет действующих значений `APP_SECRET`, `JWT_PASSPHRASE` и
  пароля к базе данных развёрнутой системы

### Requirement: Доступ к документации API

Документация API SHALL быть доступна по `https://bankrot.shefcode.tech/api/doc`
и MUST требовать HTTP Basic-авторизацию пользователя с ролью `ROLE_ADMIN`.

#### Scenario: Администратор открывает документацию

- **WHEN** пользователь с ролью `ROLE_ADMIN` открывает `/api/doc` и вводит свои
  учётные данные
- **THEN** отображается страница документации API

#### Scenario: Анонимный запрос документации

- **WHEN** `/api/doc` открывается без учётных данных
- **THEN** возвращается ответ 401 с запросом HTTP Basic-авторизации
