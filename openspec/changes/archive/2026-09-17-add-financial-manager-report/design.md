## Context

Мотивация и объём — в `proposal.md`, наблюдаемое поведение — в `specs/`. Здесь
только то, что определяет способ реализации.

Путь поля от базы до документа и до индикатора заполненности сейчас держится на
соглашениях, и новые поля обязаны их соблюсти:

1. **API.** `ContractorService::serializeContractByStages()` нормализует `Contracts`
   по группам `#[Groups]` через `ObjectNormalizer` с `AttributeLoader`. Даты уходят
   в ISO 8601, `decimal` — строкой. Геттер без свойства попадает в ответ, если
   атрибут `#[Groups]` стоит на методе.
2. **Сохранение.** `PUT /contracts/{id}` передаёт каждый раздел в
   `ContractorService::updateContractFields()`. Тот через Reflection зовёт
   `set<Key>`; даты распознаёт только по спискам `$dateFields` / `$dateTimeFields`;
   ключи без сеттера молча пропускает.
3. **Документ.** `EntityDataResolver` разрешает `{{ path }}` через геттеры.
   Для однокомпонентного пути результат проверяется через `empty()`, поэтому
   строка «0» превращается в пустую.
4. **Индикатор заполненности.** `DocumentTemplateProcessor::extractFields()` для
   каждой переменной шаблона ищет свойства `Contracts`: напрямую или разбором тела
   геттера регулярными выражениями, заходя в статические вызовы только
   `PreCourtMethods::` и `ProcedureInitiationMethods::`. Вкладку берёт из
   `#[Groups]` свойства. Вызовы функций (`ТЕКУЩАЯ_ДАТА(...)`) пропускаются.
   Фронтенд (`documentFieldsValidator.ts`) ищет подпись поля в DOM по
   `[for="<стадия>.<поле>"]` и аккордеон — по `data-radix-accordion-item`. Если
   подписи нет, поле не показывается в списке незаполненных. Вкладки и аккордеоны
   смонтированы всегда (`forceMount`), переход к полю — прокрутка к подписи и клик
   по ней.
5. **Карточка дела.** `convertApiDataToFormValues()` раскладывает раздел
   `judicial_procedure_initiation` поле за полем, а `judicial_procedure` — spread.
   Сохранение отправляет оба раздела целиком. Раздела `judicial_report` в типах
   формы нет. `Report.tsx` берёт документы из `contractData.report`, а API отдаёт
   их под `judicial_report`.
6. **Справочник финуправляющих.** `FinancialManagerController` собирает ответы
   массивами вручную. `CacheService` его не кэширует. Карточка дела получает
   управляющих из общего запроса справочников (`queryKey ["references", "all"]`);
   `normalizeItem` пробрасывает все поля элемента.

## Goals / Non-Goals

**Goals:**

- Каждый плейсхолдер из `specs/documents/financial-manager-report` разрешается
  обычным механизмом `{{ path }}`, без изменений в разборе шаблона.
- Индикатор заполненности на вкладке «Отчёт» видит новые поля и ведёт к ним.
- Существующие шаблоны после изменения генерируются тем же текстом.

**Non-Goals:**

- Разбор `Contracts` на сущности по стадиям.
- Функция шаблонизатора, принимающая путь к данным (`ДАТА(path, маска)`).
- Серверная валидация полей дела — её нет и у существующих полей.
- Исправление особенностей индикатора: поля из условных формулировок
  (`changedLastName` у несменившего фамилию) по-прежнему выглядят незаполненными.

## Decisions

### 1. Новые поля — колонки `Contracts`, а не отдельная сущность

23 nullable-колонки в `contracts` с `#[Groups]` своей стадии. Так без доработок
работают сериализация по стадиям, сохранение через Reflection и определение
вкладки индикатором.

Отклонено: OneToOne-сущность `ContractProcedureDetails`. Она потребовала бы новой
ветки в `updateContractFields()`, группы на связи, доработки
`findFieldsInfo()` для вложенного пути и отдельной раскладки на фронтенде — и всё
это ради разгрузки god-object, которую `CLAUDE.md` велит делать отдельным
предложением.

### 2. Форматированный текст — геттеры `*Text` в `Contracts`

Даты в виде «02» июля 2025 г., суммы «7 866,05», перечни — геттеры `Contracts`,
делегирующие в статический класс. Геттер обращается к свойству через
`$this->…`, поэтому индикатор находит исходное поле и его вкладку.

Отклонено: функция `{{ ДАТА('propertyInventoryDate', '«дд» ММММР гггг') }}`.
`extractFields()` пропускает функции — индикатор перестал бы видеть семь дат
отчёта. Кроме того, `CustomFunction` вызывается до разрешения путей и без
доступа к делу.

### 3. Новый класс `Service/Templates/JudicialReport/ReportMethods`

Формулировки стадии отчёта — в отдельном классе по образцу
`PreCourtMethods` / `ProcedureInitiationMethods`. `analyzeMethodRecursive()`
сейчас перечисляет два класса вручную: перечень переносится в константу, и
`ReportMethods` добавляется в неё. Без этого индикатор не увидит поля, прочитанные
внутри методов нового класса.

Общие форматтеры, которые понадобятся и остальным документам пакета, — статикой
рядом с существующим `DateHelperService`:

- `DateHelperService::formatGenitive(?DateTimeInterface): string` — «дд» месяц
  гггг г.;
- `MoneyHelperService::format(?string): string` — «7 866,05», пустое — «0,00».

Существующий `procedureInitiationDateForPublication` не переписывается, чтобы не
задеть уже работающие шаблоны.

### 4. Вычисляемые значения — формула на бэкенде, повтор в интерфейсе

Дата закрытия реестра, «всего рассмотрено», размер расходов на газеты и четыре
непогашенных остатка — геттеры `Contracts` с `#[Groups]` на методе и без сеттера.
Переданное в `PUT` значение `updateContractFields()` пропускает само.

Интерфейс считает те же значения из текущих значений формы, чтобы показывать их
до сохранения (`useWatch`).

- **Дата + 2 месяца.** В PHP `modify('+2 months')` переполняет день
  (31.12 → 03.03), поэтому год и месяц считаются явно, а день ограничивается
  числом дней целевого месяца. На фронтенде `date-fns/addMonths` ведёт себя так
  же. Совпадение закрепляется юнит-тестом бэкенда на три даты из спецификации.
- **Суммы.** Разность считается в копейках целыми числами и форматируется
  обратно в строку `"530.88"`, без арифметики с плавающей точкой.

Отклонено: хранить вычисляемые значения колонками. Они расходились бы с
исходными данными при каждом изменении стоимости публикации или даты.

### 5. Продление процедуры — enum и JSON-массив с общим инвариантом

`procedureExtensionStatus` — backed enum `Entity\Enum\ProcedureExtensionStatus`
(`extended`, `not_extended`, `no_acts`), `procedureExtensionDates` — JSON-массив
строк `ГГГГ-ММ-ДД`, как `children`. Оба ключа разбираются одной веткой
`updateContractFields()` и записываются одним методом сущности
`changeProcedureExtension(?ProcedureExtensionStatus, array)`, который обнуляет
даты при статусе, отличном от `extended`. Порядок ключей в запросе поэтому не
важен.

### 6. Отдел ЗАГС по умолчанию — константа с двух сторон

Бэкенд: `getZagsDepartmentText()` возвращает сохранённое значение или константу
`Contracts::DEFAULT_ZAGS_DEPARTMENT`. Фронтенд: та же строка в `defaultProcedure`
и в раскладке ответа, если поле не пришло. Интерфейс показывает текст сразу, и
индикатор считает поле заполненным.

Отклонено: возвращать текст по умолчанию из `getZagsDepartment()`. Тогда API
отдавал бы значение, которого нет в базе, и нельзя было бы отличить «не
заполнено» от «заполнено текстом по умолчанию».

### 7. Полис страхования — статус считает сущность, дату даёт контроллер

`FinancialManager::getInsuranceStatus(DateTimeInterface $today): InsuranceStatus`
— чистый метод с enum `Entity\Enum\InsuranceStatus` (`valid`, `expired`,
`missing`). Контроллер передаёт `new DateTimeImmutable('today')` и добавляет
`insuranceEndDate` (`Y-m-d`) и `insuranceStatus` в `serializeFinancialManager()`
и `serializeFinancialManagerFull()`. `symfony/clock` в проекте не установлен;
тесты задают срок полиса относительно реального сегодня (вчера, сегодня, завтра).

`getInsuranceContractDescription()` собирает строку для документа и пропускает
незаполненные части.

Предупреждение на фронтенде — один компонент `shared/InsuranceStatusAlert` в
четырёх местах из спецификации. Карточка дела берёт статус у выбранного
управляющего из `referenceData.financialManagers`. После создания и изменения
управляющего форма вызывает `invalidateQueries({ queryKey: ["references"] })`,
иначе карточка дела показывала бы старый статус до перезагрузки.

### 8. Блоки на вкладках — аккордеоны, а не третий уровень табов

Заказчик называет «Публикации», «Расходы» и т. п. вкладками внутри разделов.
Интерфейс реализует их как `AccordionItem` внутри карточек «Введение процедуры»
и «Процедура», раскрытые по умолчанию (`type="multiple"` со всеми значениями в
`defaultValue`, как на вкладке «Основная информация»).

Причины: индикатор определяет место поля по `data-radix-accordion-item`, а
переход к полю прокручивает к подписи — у свёрнутой секции прокручивать некуда.
Третий уровень табов под «Судебка → Введение процедуры» сломал бы
`navigateToField`, который знает только два уровня.

Подписи получают `htmlFor="<стадия>.<поле>"`, совпадающий с полем, которое
возвращает `extractFields()`. У списка дат продления такой подписи нет
намеренно: иначе индикатор требовал бы даты и при варианте «не продлевалась».

### 9. `EntityDataResolver`: ноль — это значение

Для однокомпонентного пути проверка `empty($value)` заменяется на `$value === ''`.
Затронуто только значение «0», которое ни один существующий плейсхолдер сейчас не
возвращает.

### 10. Маска `ММММР`

В `CustomFunction::formatDate()` замена `ММММР` выполняется раньше `ММММ` и
берёт название из `DateHelperService::getMonthNameGenitive()`. Остальные маски
не меняются.

### 11. Шаблон хранится в репозитории

Размеченный `.docx` кладётся в `backend/src/document-templates/` — папка уже в
git (`9_sov_kom_bank.xlsx`). Загрузка на окружения — через `/documents`, как у
остальных шаблонов. Файл в репозитории нужен функциональному тесту: он
генерирует отчёт по фикстурному делу и проверяет, что `{{` в `word/document.xml`
не осталось, а ключевые значения подставлены.

### 12. Миграции

Две миграции Doctrine: `financial_managers` (+4 колонки) и `contracts`
(+23 колонки). Все колонки nullable, без переноса данных — миграции обратно
совместимы, старый код с новой схемой работает. Откат — `down()`, при нём
данные новых полей теряются.

## Risks / Trade-offs

- [PhpWord не находит плейсхолдер, разорванный Word-ом на несколько runs,
  особенно в 19 таблицах формы] → каждый плейсхолдер вводится одним куском без
  автозамены кавычек; тест из решения 11 падает, если в документе остался `{{`.
- [Наименования ГИМС МЧС, Гостехнадзора и ФНС из справочников записаны для шапки
  запроса и в середине предложения могут не согласоваться по падежу] →
  зафиксировано в спецификации; при жалобах заказчика — отдельное поле падежной
  формы в справочниках.
- [Формулы вычисляемых значений продублированы на фронтенде] → формулы
  тривиальны, кроме переноса даты, а он покрыт тестом и совпадает с поведением
  `date-fns`.
- [Итоговые строки очередей в разделе 4.8 остаются статичными «0,00», хотя строки
  первой очереди заполняются] → документ внутренне несогласован; вынесено в
  открытые вопросы.
- [Данные управляющего, не размеченные в форме (ФИО, СРО, адрес), остаются
  постоянным текстом] → отчёт корректен только для Федорца В. В.; другой
  управляющий требует правки шаблона. Решение заказчика по разметке.
- [`Contracts` вырастает ещё примерно на 600 строк] → известный техдолг, не
  усугубляется новыми механизмами.

## Migration Plan

1. Выложить бэкенд: миграции применяются на сервере целью `make db-migrate`.
2. Выложить фронтенд.
3. Загрузить шаблон из `backend/src/document-templates/` через `/documents` в
   категорию «Судебка отчет» на каждом окружении.
4. Внести полис Федорца В. В. в справочник.

Откат: выложить предыдущую версию, затем при необходимости `down()` миграций.
Шаблон отчёта удалить через `/documents`.

  «ИТОГО ПО ВСЕМ ОЧЕРЕДЯМ») из четырёх позиций расходов. Добавит три геттера и
  плейсхолдера, подход не меняется.
- Точное место блоков «Расходы на проведение процедуры» и «Фиктивные и
  преднамеренные признаки банкротства»: заказчик не указал раздел, в плане они на
  вкладке «Процедура». Перенос — перемещение аккордеона.
