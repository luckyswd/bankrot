# CLAUDE.md

Система ведения дел о банкротстве физических лиц в РФ (ФЗ № 127-ФЗ).
Пользователи — юристы: ведут дело должника по пяти стадиям процедуры и
генерируют пакеты документов (`.docx` / `.xlsx`) из шаблонов.

Глоссарий предметной области: @CONTEXT.md

---

## Структура

```
backend/    Symfony API        -> подробные правила в backend/CLAUDE.md
frontend/   React SPA          -> подробные правила в frontend/CLAUDE.md
docker/     nginx, php, mysql, node
openspec/   рабочий процесс OpenSpec
```

Прежде чем править код в `backend/` или `frontend/`, прочитай `CLAUDE.md`
соответствующей папки — там стек, команды и конвенции этой части проекта.

## Команды

```bash
make          # список доступных целей
make up       # подготовить .env и поднять контейнеры
make down     # остановить и удалить контейнеры
make sh       # shell в контейнере php
```

Проверки бэкенда проксируются в контейнер, запускай из корня:

```bash
make check-code   # stan + lint
make test         # PHPUnit
```

Адреса: фронтенд — http://localhost, API — http://api.localhost,
документация API — `/api/doc` (HTTP Basic, требуется `ROLE_ADMIN`).

## Правило первое: комментарии не пишем

**Не оставляй в коде объясняющих комментариев.** Ни `//` с описанием того, что
делает строка, ни PHPDoc-блоков вида «Сериализует контракт, группируя данные по
стадиям», ни закомментированного кода, ни `TODO` / `FIXME`.

Код должен быть самодокументируемым: понятные имена, короткие функции, явные
типы. Тянет написать комментарий — переименуй сущность или выдели метод с
говорящим названием.

Единственное исключение — PHPDoc, несущий типовую информацию, невыразимую в
сигнатуре:

```php
// Запрещено
/**
 * Возвращает все значения перечисления.
 */
public static function getValues(): array

// Разрешено
/**
 * @return array<int, string>
 */
public static function getValues(): array
```

Во фронтенде правило то же. JSDoc не используем — типы описываются в TypeScript.

Существующий код этому правилу пока не соответствует: в `ContractorService`,
`DocumentTemplateProcessor` и `PreCourtMethods` много старых описательных
PHPDoc. Массово их не вычищаем, но в новом и переписанном коде комментариев
быть не должно.

## Что нужно знать про домен до правки кода

**`App\Entity\Contracts` — это дело о банкротстве целиком** (карточка клиента),
а не «договор». Номер договора с клиентом — лишь поле `contractNumber` внутри
неё. Экран `/contract/:id` рендерит `ClientCard`.

**Enum `BankruptcyStage` выполняет три роли одновременно:**

1. стадия жизненного цикла дела — `basic_info` -> `pre_court` ->
   `judicial_procedure_initiation` -> `judicial_procedure` -> `judicial_report`;
2. группа сериализации Symfony — каждое поле `Contracts` помечено
   `#[Groups([BankruptcyStage::BASIC_INFO->value])]`;
3. категория шаблона документа — `DocumentTemplate::$category`.

Отсюда сквозное правило: **новое поле `Contracts` без `#[Groups]` не попадёт в
ответ API и будет невидимо на фронтенде.** Добавление поля — это всегда работа
с обеих сторон: атрибут в сущности плюс отображение в нужной вкладке `ClientCard`.

**Восемь однотипных справочников** — `Court`, `Creditor`, `Bailiff`,
`FinancialManager`, `Fns`, `Mchs`, `Rosgvardia`, `Gostekhnadzor` — имеют
идентичный CRUD с обеих сторон. Меняешь один — проверь, нужно ли то же в остальных.

## CI и ветки

`.github/workflows/staging.yml` на push в `staging`: PHPStan -> PHP CS Fixer ->
PHPUnit -> FTP-деплой. Джобы бэкенда запускаются только при изменениях в `backend/`.
CI вызывает цели `make stan`, `make lint`, `make test`, `make jwt-gen` из
`backend/Makefile`, а на сервере — `make composer-install`, `make cc`,
`make db-migrate`. **Переименовывать эти цели нельзя.**

Рабочая ветка — `staging`, основная — `main`.

---

## OpenSpec

Настроен OpenSpec (`openspec/`, схема `spec-driven`). Для нетривиальных изменений
сначала оформляй предложение (`/opsx:propose`), а не правь код сразу. Контекст и
правила артефактов — в `openspec/config.yaml`.
